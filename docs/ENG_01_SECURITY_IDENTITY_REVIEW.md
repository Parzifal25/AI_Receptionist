## Findings (ranked)

### SEC-01 — Widget runtime does not fail closed on invalid persisted agent identity

- **Severity:** High (identity integrity; conditional on stale or inconsistent row)
- **Evidence class:** Confirmed code behavior; exploitability from public input not established.
- **Locations:** `src/app/api/v1/widget/messages/route.ts`; `packages/agents/agent-repository.ts`; `supabase/migrations/0030_production_version_guards.sql:1-34`.
- **Scenario at initial review:** If a conversation had no agent/version linkage, or the tenant-scoped version lookup returned no row, the route ran the receptionist compatibility context instead of rejecting the turn. If lookup returned a same-tenant version for another agent, the route accepted its prompt/config without checking `version.agentId === conversation.agentId`; it also did not require `publishedAt`. This allowed stale or inconsistent rows to select unintended or unpublished context. Request-body IDs remained ignored and foreign-tenant versions were filtered by business ID; no public write path to such a row was established.
- **Existing test evidence (before remediation):** `tests/integration/widget-messages-security.test.ts` proved request identity was ignored and foreign-tenant versions did not resolve, but its foreign-version case expected receptionist fallback. `tests/integration/agent-linkage.test.ts` and `scripts/check-rls.mjs` cover database ownership guards for writes.
- **Remediation (local source):** The messages route now requires both non-empty persisted IDs, loads the version under the conversation tenant, and verifies its business ID, agent ID, and `publishedAt` before constructing runtime context. Missing, partial, unresolved, foreign-tenant, wrong-agent, and draft tuples return the same non-sensitive 409 response before model execution or turn writes. The implicit receptionist fallback has been removed. Normal receptionist widget conversations remain supported through the pinned published receptionist agent. ENG-03 also removed the separately gated null-link creation path.
- **Regression test and acceptance (local):** `tests/integration/widget-messages-security.test.ts` covers missing IDs, partial/unresolved IDs, conversation/receptionist tenant mismatch, a same-tenant version belonging to another agent, an unpublished version, a foreign-tenant version, body-supplied identity being ignored, and a valid pinned published receptionist version. Invalid cases assert no model call or message/state writes; the valid case asserts the exact pinned prompt and the existing response envelope. The earlier combined creation/message result was 21/21; fresh broader focused results are recorded above (79 Vitest tests across widget, resolver/versioning, gateway and authorization harnesses). Existing-row database audit and deployed migration/data evidence remain outstanding.
- **Release impact:** Local route remediation is complete. **Pilot authorization remains blocked** until deployment-boundary review and malformed existing rows are dispositioned. This source-level remediation alone is not deployed security verification. **Blocks GA** under criterion 2 and mandatory security gate.

### SEC-04 — Widget start could create an unserviceable null-linked conversation

- **Severity:** High correctness/identity-boundary risk when the legacy flag is enabled; no public identity selection was found.
- **Evidence class:** Confirmed source behavior and explicit temporary compatibility switch.
- **Locations:** `src/app/api/v1/widget/conversations/route.ts`; `src/core/services/widget-repository.ts`; `packages/platform/env.ts`; migrations `0014`, `0015`, `0021`, `0022`, `0030`.
- **Compatibility contract found:** `HALO_AGENT_RESOLUTION_COMPAT_FAIL_OPEN` explicitly allowed only the classified `agent_not_found` case to start a row with null agent IDs, for pre-0014 tenant backfill compatibility. It did not accept caller-supplied agent identity. Migrations `0014` and `0022` backfill existing receptionists; `0021` provisions them for new businesses. The web widget creation path is the sole caller of `WidgetRepository.createConversation`. The separate production phone path uses `SupabaseCallStore.beginCallConversation`/`begin_call_conversation` with IDs from the tenant-bound call route. `createPhoneConversation` also requires both IDs by type, but no production call site was found. The widget client's request and success envelope remain unchanged: `{ data: { visitorToken, greeting } }`.
- **Why retire it:** After ENG-02, the message route correctly refuses a null-linked conversation, so the flag admitted starts that could not receive turns. The local migration design provides tenant-bound receptionist-agent resolution for existing and newly created businesses. The compatibility flag therefore no longer preserves a usable client flow; any tenant still missing the migration/backfill must fail closed and be resolved through owner-approved deployment/data remediation.
- **Remediation (local source):** All resolver errors now return the existing generic 503 without inserting a conversation. `WidgetRepository.createConversation` requires non-null agent and version IDs at the type boundary and always persists both. The obsolete environment setting was removed from the server schema. No database schema or historical row was changed.
- **Regression test and acceptance (local):** `tests/integration/agent-linkage.test.ts` verifies a valid published receptionist version is pinned; existing widget client fields and response shape remain compatible; missing agent resolution fails even when the retired environment variable is set; and foreign-tenant agent/version candidates create no conversation. The combined creation/message suites passed (2 files, 21 tests); targeted ESLint and `git diff --check` passed.
- **Persisted-data assessment:** Local migrations leave `conversations.agent_id` and `agent_version_id` nullable (`0015`), and both foreign keys use `ON DELETE SET NULL`; `0030` does not enforce non-null identity on insert. `0015` backfills rows only when it finds an active receptionist agent. Therefore null or partial tuples remain structurally possible from pre-backfill data, missing/incomplete deployment migrations, or deletion of linked agent/version rows. Their presence in production is unknown. Do not backfill by guessing a tenant's current agent, because historical conversation identity cannot be proved that way.
- **Migration sequence and expected evidence:** In the ordered migration set, `0014_agent_backfill.sql` creates receptionist agents and published version 1 for receptionists existing at that migration. `0015_conversation_agent.sql` adds nullable conversation agent/version foreign keys and backfills conversations against an active receptionist agent; it does not make either field mandatory or establish a database check that the version belongs to the conversation's agent. `0021_business_creation_provisions_agent.sql` provisions a receptionist agent/version for new businesses after the one-time `0014` backfill. `0022_backfill_agents_created_after_0014.sql` repairs the onboarding window before `0021`. These migrations are separated by other migrations; the target ledger must show each relevant version applied in sequence. The target's application revision must be recorded alongside the ledger because application code and migrations can be deployed separately.

The independent foreign keys do not prove tenant or agent-pair equality. Migration `0030` rejects an unpublished referenced version, but its conversation trigger does not require non-null IDs or verify `agent_versions.agent_id = conversations.agent_id` and matching tenant on insert.
```sql
begin transaction read only;
select
  count(*) filter (where c.agent_id is null) as null_agent_id,
  count(*) filter (where c.agent_version_id is null) as null_agent_version_id,
  count(*) filter (where c.agent_id is not null and a.id is null) as missing_agent_row,
  count(*) filter (where a.id is not null and a.business_id <> c.business_id) as cross_tenant_agent,
  count(*) filter (where a.id is not null and (a.type <> 'receptionist' or a.slug is distinct from c.receptionist_id::text)) as receptionist_agent_mismatch,
  count(*) filter (where c.agent_version_id is not null and v.id is null) as missing_agent_version_row,
  count(*) filter (where v.id is not null and v.business_id <> c.business_id) as cross_tenant_agent_version,
  count(*) filter (where v.id is not null and v.agent_id is distinct from c.agent_id) as agent_version_mismatch,
  count(*) filter (where v.id is not null and v.published_at is null) as unpublished_version
from public.conversations c
left join public.agents a on a.id = c.agent_id
left join public.agent_versions v on v.id = c.agent_version_id;
commit;
```

The counters are independent and may overlap; do not sum them as a total number of affected rows. ### SEC-06 — Legacy conversation backfill could select another receptionist in the same tenant (fixed locally)

- **Severity:** Medium identity-integrity defect. No cross-tenant disclosure was found; a valid conversation could run with another receptionist profile's agent/version and mismatched context.
- **Evidence class:** Reproduced deterministically in a fresh disposable migration replay with two receptionist rows in one tenant.
- **Locations:** `supabase/migrations/0014_agent_backfill.sql`, `supabase/migrations/0015_conversation_agent.sql`, `src/app/api/v1/widget/messages/route.ts`, `tests/integration/widget-messages-security.test.ts`, `scripts/check-migrations.mjs`.
- **Cause:** Migration `0014` creates one receptionist agent per receptionist, keyed by `agents.slug = receptionists.id`. Migration `0015` selected the first active receptionist agent for the whole business and assigned it to every legacy conversation, ignoring each conversation's persisted `receptionist_id`. With multiple receptionist records, the wrong profile could be assigned. The widget message route previously checked only tenant and version/agent consistency, so this same-tenant mismatch could reach the model.
- **Local remediation:** Migration `0015` now joins to the exact `receptionist_id` via the seeded agent slug and leaves the tuple null if there is no exact match. The widget message route now verifies the pinned agent is a receptionist agent whose slug matches the conversation's `receptionist_id`, returning the same opaque conflict before model execution or writes otherwise. This guard also fails closed for rows produced by an already-applied copy of the old migration.
- **Regression evidence:** `scripts/check-migrations.mjs` seeds two receptionist identities and legacy conversations before migrations `0014`/`0015`, verifies both agent/version tuples map to their exact receptionist, then replays the migrations declared idempotent and rechecks the links. The message route test verifies a same-tenant but wrong-receptionist tuple produces no model call, message, usage event or state write. Fresh focused/full and disposable database results are in the 2026-10-12 Alpha checkpoint.
- **Historical-data boundary:** No existing development or hosted database was queried or altered. If any environment already applied the old `0015`, wrong links are unknown, not zero. Do not rewrite historical rows: although `receptionist_id` identifies the receptionist, it may not prove the exact historical immutable agent version. Proposed ENG-12's target audit includes a receptionist/agent mismatch aggregate; any row-level repair requires reliable version evidence and authorized migration design.
- **Release impact:** Corrected and regression-tested for local Alpha. Existing target data remains a Beta/final-release audit and disposition item; criteria 2's deployed identity evidence stays open for those later phases.

### SEC-05 — Conversation-start identity consistency (remediated locally)

- **Severity:** Low (conditional identity consistency gap; no public exploit path established).
- **Evidence class:** Confirmed source behavior; trigger condition and practical exploitability are unverified.
- **Locations:** `src/app/api/v1/widget/conversations/route.ts`; `packages/agents/agent-resolver.ts`; `src/core/services/widget-repository.ts`; `supabase/migrations/0030_production_version_guards.sql`.
- **Scenario (confirmed before remediation):** Conversation start resolved the widget key into `business` and `receptionist`, then the resolver independently looked up that key again. The route discarded `resolved.businessId` and inserted with the first lookup's business/receptionist. A remap between reads could therefore pair tenant B's agent/version with tenant A's conversation identity. Migration `0030` checks publication on conversation insert but does not check agent/version tenant or pair ownership; the foreign keys are independent. Downstream message handling fails closed on tenant mismatch, but the mixed row could already exist.
- **Reachability limits:** Repository search found no application write path that rotates `receptionists.widget_key`; the column is unique. A concurrent privileged change or inconsistent backing store is therefore required for the described condition. The new regression simulates a key remap after the first lookup; no target database was inspected.
- **Remediation (local source):** The route now resolves the agent by the `business.id` and `receptionist.id` from its first validated widget-key lookup. It performs no second widget-key lookup. Before insertion it checks that the receptionist, resolved tenant, agent, version, and agent/version relationship all match that selector. Resolver or tuple failures use the existing opaque 503 path, before a conversation row or success event is written. The widget client's successful request and response contract are unchanged.
- **Regression and fresh local evidence (2026-10-12):** `tests/integration/agent-linkage.test.ts` remaps the key backing row from tenant A to tenant B immediately after the first lookup, while making only tenant B's agent/version available. Start returns 503 and records no conversation insert. The same focused run also covered normal start/client compatibility, widget-message security, and two-tenant isolation: `npx vitest run tests/integration/agent-linkage.test.ts tests/integration/widget-messages-security.test.ts tests/integration/multi-tenant-isolation.test.ts` passed 3 files / 29 tests. This is local harness evidence on the dirty worktree, not a clean-checkout or deployment revalidation.
